## 1. 参照元実装の精査結果（T1.13 のうち JV-Link 部分）

### 1.1 使用している JV-Link API
| API | 用途 [参照元] | 備考 |
|---|---|---|
| `Dispatch(ProgID)` | `JVDTLab.JVLink` ほか 6 つの ProgID、CLSID `{2AB1774D-0C41-11D7-916F-0003479BEB3F}`、CoCreateInstance の順に試行 | 32bit COM。64bit Python では不可（README/docs も 32bit Python を要求） |
| `JVSetSavePath` / `JVSetPort` | 保存先（既定 `C:\TFJV` があれば使用）、`agent_port` 6531 | 存在確認して分岐（`hasattr`） |
| `JVInit(sid)` | `JVLINK_SID` / 設定 / `"UNKNOWN"` | エラーコード表（-101〜-108 の独自文言）あり。**公式の戻り値と一致するか疑わしい** [要確認] |
| `JVOpen(dataspec, fromtime, option, 0,0,"")` | 蓄積系（`RACE`、補てん `RCVN`/`RCOV`）。`option` 候補 `[2,0,1]`（RACE）/`[2,0]`（補てん）。戻り値 `(ret, readcount, downloadcount, lastfiletimestamp)` | `option=0` は公式の値か不明 [要確認]。`ret=-1` なら fromtime を `00000000000000` にリセット再試行 |
| `JVRTOpen(dataspec, key)` | 速報系: `0B30/0B31/0B33/0B35`（オッズ, key=16桁レースキー）、`0B12`（成績, key=YYYYMMDD）、`0B15`（払戻 HR, key=YYYYMMDD） | `-413` で 1s→2s バックオフ（最大計3回）。`-413` 時はキャッシュキーを 60 秒に1回だけ破棄 |
| `JVRead(buff,size,fname)` | `ret>0` レコード、`-1` ファイル切替、`-3` ダウンロード中（0.5s 待機）、`0` EOF、`-402/-403` ファイル異常→`JVSkip`、`-503` はバッファ拡張（最大 2,000,000） | 総読込上限 50,000（RACE）/ 200,000（補てん）。**文字列で返る**ため `cp932` に再エンコードしてバイト位置で切出し（`errors="ignore"`） |
| `JVSkip` | ファイル先頭レコードが `SE` なら `RACE` 取得時にスキップ | 先頭レコード種別で判断する保守的ヒューリスティック |
| `JVClose` | 各取得の最後（例外時も） | — |
未使用: `JVGets`（バイト列取得）、`JVStatus`、`JVFiledelete`、`JVFukuFile`、`JVWatchEvent`（イベント通知）、`JVMVOpen`、`JVCancel` ほか。 [要確認: 存在と仕様]

### 1.2 データ種別（dataspec）の使用実態

|---|---|---|---|---|---|

| `RCVN`/`RCOV` | 蓄積（補てん） | 馬マスタ(UM)・過去走(SE) の蓄積（`ingest_cover_data`） | UM KS CH BR BN RC RA SE | fromtime（RCOV は日付境界へ丸め） | **「補てん情報（レース情報）」＝非蓄積系ソフト向け**で、過去を貯める用途では本来不要 [二次]。参照元の `-111` 試行錯誤はこの種別が環境依存であることを示す |

→ **参照元は開催変更系（YSCH, 0B14）を使っていない**。新設計では T1.3 のために YSCH と 0B14 を追加する。

### 1.3 差分取得・最終取得時刻
- `lastfiletimestamp`（JVOpen の出力）を `jvlink_timestamps` に data_type 別で保存し、次回 `fromtime` にする [参照元]。`RACE` は `race_days_back` で下限を引き下げ。
- 保存は「JVOpen 成功時」。**読込が完走したか（EOF まで）とは独立** → 読込途中で失敗しても fromtime が進んでしまう欠損リスク [参照元の弱点]。
- 新設計: **ACK 後にのみ進める**（§5）。fromtime は取得時刻（提供時刻）であってレース日ではない [二次]。

### 1.4 パーサ（固定長 Shift_JIS）
`_slice_sjis`: 文字列を `cp932` にエンコードし、1 始まりバイトオフセットで切出して再デコード [参照元]。

| O1 | 発売フラグ(40)、44 から 8 バイト×28（馬番2, オッズ4=×0.1, 人気2） | 同上 |
| O3 | フラグ(40)、41 から 17 バイト×153（組4, 下限5, 上限5, ほか） | 同上 |
| O5 | フラグ(40)、41 から 15 バイト×816（組6, オッズ6, ほか） | 同上 |

**疑義・欠陥候補（新実装では再現せず、正を仕様書で確認）**:
1. **HR 単勝払戻の解釈**: 9 桁を「8 桁整数 + 1 桁小数」として `/100` 倍率化している。仕様書で払戻金は円単位の整数 9 桁のはずで、**10 倍ずれの可能性**がある [要確認]。参照元に払戻をオッズから逆算する補完スクリプト（`backfill_results_payout.py`）があることも不信の傍証。
2. **レース ID が 12 桁（回・日目なし）**: `JVRTOpen` 用 16 桁キーを復元できず、回 01〜03×日目 01〜02 を総当たり（6 候補）。新設計は **`race_id`(12桁) + 回(`kai`)・日目(`nichime`) を保持し、16桁 `rt_key` を導出**（D-040、サーバ側が plan にキーを載せるため総当たり不要）。
3. **文字列経由の再エンコード**: COM が返す文字列を `cp932` に戻すため、変換不能文字が `errors="ignore"` で欠落。バイト位置がずれる可能性がある。→ **バイト列（`JVGets` 等）を送る**（§4.3）。ただし API 仕様は [要確認]。
4. **JVInit エラー表が独自**: 公式の戻り値と異なる可能性（第三者資料の認証系は -301/-303/-305 等）。公式表に置換。
5. **`option=0`** の使用: 公式値か不明。公式は 1=通常、2=今週、3/4=セットアップ [二次: 1と4のみ確認]。
6. **状態がメモリ上**: `result_fetched` や各種キャッシュがプロセス内のため再起動で再取得（冪等でないと二重通知/二重決済）。新設計は DB 管理。
7. **例外握り潰し**: `except: pass` が多数。新設計は失敗を構造化して記録・通知。
8. **`datetime.now()`（naive）** でのウィンドウ計算。→ Clock(Asia/Tokyo)。
9. **`-413` の扱い**（キャッシュ破棄の頻度制限）は経験則。新設計ではサーバが 16 桁キーを渡すので不要。

### 1.5 エラー・リトライ・再接続・再取得（参照元）
- `JVRead` の `-3` は 0.5s 待機でリトライ、`-402/-403` は `JVSkip`、`-503` はバッファ拡張。総読込回数の上限で無限ループ防止。
- 取得失敗の再接続戦略は無い（プロセス常駐でループ全体をリトライ、`error_wait_seconds=60`）。
- 取りこぼし対策は `race_days_back` のみ。結果の取りこぼしは `backfill_*` スクリプトで人手。
- 新設計: **ACK ベースのチェックポイント + オーバーラップ読み直し + サーバ側冪等**（§5）。

## 3. 方式比較: エージェントの実装言語
| 案 | 概要 | 利点 | 欠点 | 評価 |
|---|---|---|---|---|
| **P1 Python（64bit または 32bit）** | 参照元の COM 呼出しパターンを再利用。pywin32、PyInstaller で exe 化 | 動作実績のある呼出し手順を流用、薄いエージェントなら数百行、デバッグ容易、32bit/64bit 両対応を設定で切替 | Python 実行環境の同梱、pywin32 の COM 型変換（文字列/バイト）が癖 | **推奨（第一段階）** |
| P2 C#/.NET（Windows 専用） | 公式サンプル・構造体定義（JVData_Struct.cs）が C#/VB 中心 | COM 相互運用が最も素直、`Platform=x86/x64` 切替、単一 exe 配布、Windows サービス化しやすい | プロジェクトに第3の言語（Kotlin/Python/C#）が増える。参照元から流用できるコードがない | 代替（P1 で配布・安定性に問題が出た場合） |
| P3 Kotlin/JVM（JACOB/JNA で COM） | サーバと言語統一 | 言語統一、パーサ共有 | COM ブリッジの 32/64bit・DLL 配布が脆い、小規模エージェントに JVM は重い | 非推奨 |
| P4 PowerShell | COM 呼出しは容易 | 依存なし | 長時間常駐・キュー・テストが不向き | 非推奨 |
**決定案（D-018）**: **P1 Python を第一段階の実装とし、エージェントを「薄く」保つ**（パース・業務ロジックは持たない）ことで、将来 P2 への置換コストを小さくする。64bit 版 JV-Link が一般提供済みなら 64bit Python、未提供なら 32bit Python で動かす（実装は同一）。ML の Python（学習ジョブ）とは**別物**で、エージェントは ML に依存しない。根拠: ①動作実績の流用、②Windows 固有部分が COM 呼出し数十行に限定される、③言語を増やさない。**ゲート**: T3 で 64bit JV-Link + pywin32 の組合せが動くことを確認（動かなければ P2）。

## 4. Windows とサーバ（Kotlin）の分担

### 4.1 役割
| Windows エージェント（薄い） | サーバ（Kotlin: ingest + bot） |
|---|---|
| JV-Link セッション管理（Init/Open/Read/Close、タイムアウト、再接続） | 認証・認可、運用モード判定、重複排除 |
| サーバの**実行計画（plan）**に従って取得（何を・いつ・どのキーで） | 取得計画の生成（開催カレンダー + 手動補正 + 欠損検知） |
| 生レコードをバイトのまま封筒に詰める（種別 ID で粗く分類） | **JV-Data 固定長パース**、正規化、DB upsert |
| ローカルキュー・チェックポイント・再送・バックオフ | 冪等処理、ACK、取込結果の返却 |
| ハートビート、自己診断（JV-Link 状態、ディスク、時計ずれ） | 欠損監視・アラート |
| 自己更新（署名検証付き） | 配布物の署名・バージョン管理 |

### 4.2 取得計画（pull 型）の利点
サーバが「いま何を取得すべきか」を返す（`GET /v1/agent/plan`）。開催日・発走時刻の変更や手動補正をサーバ側だけで反映でき、エージェントは更新不要。STOPPED では plan が `idle` になる。エージェントがインターネットから受ける接続は無い（アウトバウンド HTTPS のみ）。

### 4.3 生レコード vs 構造化 JSON
| 観点 | 生レコード転送（推奨） | エージェント側で構造化 JSON |
|---|---|---|
| パーサの置き場 | サーバ 1 箇所（Kotlin、テスト容易） | エージェント（Python）+ サーバ検証の二重化 |
| 仕様変更/誤りの修正 | サーバ修正 + **保存済み生レコードから再解析可能** | エージェント更新が必要。過去分の再解析は不可 |
| エージェントの更新頻度 | 低い（取得ロジックのみ） | 高い |
| 転送量 | 大きい（O5 は 1 レコード約 12KB）が gzip で圧縮、数百 KB/バッチ | 小さい |
| 規約面 | 生データの保管 = 保管範囲が広い。**生レコード保管も解析後データも同じ「保存」なので差は小さいが、保管期間・範囲は問い合わせ事項**（DATA_SOURCE_COMPLIANCE） | 同じ |
| 文字コード | cp932 バイトをそのまま（base64）。欠落なし | エージェントでデコード（誤りが固定化） |
**決定案（D-019）**: 生レコード転送。封筒に `dataspec`・`record_id`（先頭 2 文字）・`bytes_b64`（cp932 バイト）・`sha256` を載せる。サーバが生レコードを一定期間保管（保持期間は規約確認後に決定。既定は「パース成功確認後 30 日で削除」案）。
**注意**: COM の `JVRead` は文字列で返すため、バイト列取得（`JVGets` 等）の利用可否と pywin32 での型を第3段階の最初に検証する [要確認]。不可なら「cp932 再エンコード + 欠落検知（往復一致チェック）」にフォールバック。

### 4.4 エージェント内部構成
```
agent/
  main (loop)  : mode/plan 取得 → 取得ジョブ実行 → キュー投入 → 送信
  jvlink_worker: JV-Link を別プロセスで実行（タイムアウト付き。COM ハング時は kill→再起動）
  queue (SQLite WAL): outbox, checkpoints, dedup cache
  sender       : バッチ、gzip、署名、リトライ、バックオフ
  mode_client  : ビーコン + ingest の状態判定（CONTRACTS §7）
  updater      : 署名付き manifest の検証・差替え・ロールバック
  telemetry    : ハートビート、ローカルログ（ローテーション）
```
`jvlink_worker` を別プロセスにする理由: COM 呼出しが戻らないケースでも本体の送信・ハートビートを止めない。

## 5. 重複送信防止・チェックポイント・キュー

### 5.1 識別子
- `agent_id`: インストール時に発行（UUID）。サーバ側で登録・失効可能。
- `batch_id`: UUIDv7（時系列ソート可）。**同一バッチは同一 `batch_id` で再送**（内容不変）。
- `record_key`: `dataspec + record_id + 自然キー（`race_id`(12桁)+回・日目 or 16桁 rt_key 等）+ データ区分 + データ作成年月日 + sha256(bytes)`。サーバは `UNIQUE(record_hash)` で冪等。
- 速報オッズは `observed_at`（エージェントが JVRTOpen を呼んだ時刻、UTC）を封筒に持たせる（時系列キー）。

### 5.2 三種のチェックポイント（dataspec 別）
| 名称 | 意味 | 更新タイミング |
|---|---|---|
| `fetched_ts` | JVOpen が返した `lastfiletimestamp` と EOF 到達の有無 | JVRead が EOF まで完走した時 |
| `queued_seq` | ローカルキューに格納済みの最終連番 | 格納の永続化後 |
| **`acked_ts`** | **サーバが ACK した最終取得時刻** | サーバ ACK 受信後（コミット） |
次回 `JVOpen` の `fromtime` は **`acked_ts` から 6〜24 時間の安全マージン（オーバーラップ）を引いた値**。重複はサーバ冪等で吸収。これにより「読込途中失敗」「ACK 前クラッシュ」「STOPPED による未送信」でも欠損しない。

### 5.3 ローカルキュー（SQLite, WAL）
| 項目 | 設計 |
|---|---|
| テーブル | `outbox(seq, batch_id, dataspec, class, observed_at, payload_gz, bytes, status[PENDING,SENDING,ACKED,DEAD], attempts, next_try_at)`、`checkpoints`、`state(kv)` |
| 区分（class） | **S=蓄積系**（失うと再取得が必要。JV-Link サーバに 1 年保持されるので再取得可）、**R=速報（時系列）**（オッズは**二度と取れない**。TTL 付きで保持）、**C=制御**（ハートビート等。キューに溜めない） |
| 保持上限 | 総量 2 GB（設定可）。超過時は **R の古い順に破棄**（ログ + 次回ハートビートで通知）。S は破棄せず取得を停止（`acked_ts` が進まないだけで JV-Link サーバ側から再取得できる） |
| TTL | R: 既定 7 日（STOPPED が長引いても溜め込みすぎない）。S: 無期限（ただし上限内） |
| 送信順 | 古い順、バッチ ≤ 1 MB（gzip 後）・≤ 200 レコード |
| 暗号化 | 秘密情報（トークン）は DPAPI（Windows 資格情報）に保存。キュー内の生レコードはディスク暗号化（BitLocker）前提で追加暗号化しない |

### 5.4 リトライ規則（要点。完全版は CONTRACTS §7）
- 5xx/タイムアウトのみ指数バックオフ（1s→2s→…最大 15 分、ジッタ ±20%）。4xx（認可失敗等）は停止してアラート。
- **STOPPED（確定）/UNKNOWN 時は取得もバッチ送信も止め**、モード確認のみ間隔を伸ばして実施（5 分→15 分→60 分で頭打ち）。

## 6. PC 停止中の取得漏れ対策
| データ | 欠損の影響 | 対策 |
|---|---|---|
| 蓄積系（RACE の出馬表/確定、YSCH、DIFN 等） | JV-Link サーバに **1 年**保持 [二次]。復帰後の `fromtime=acked_ts-margin` で回復 | 自動回復。バックフィルモード（option 3/4 セットアップ、年単位に分割）も用意 |
| 速報: オッズ（0B30 系） | **取得時点でしか取れない**。保持約 1 週 [二次] でも**過去時点の再構成はできない**（時系列オッズ 0B41/0B42 は単複枠・馬連のみ・ワイド/3連複なし [二次]） | 開催日の監視ウィンドウ中は PC を起動しておく。**欠損は DEGRADED として記録**（`ingest_gap`）、その時間帯の判定は「古いオッズでは通知しない」。復旧後は欠損を明示（嘘のデータを作らない） |
| 速報: 結果/払戻（0B12/0B15） | 約 1 週保持 → 復帰が早ければ取得可。遅れても月曜 14:00 の確定成績（RACE）で補完 | `reconcile` ジョブで確定成績から補完（冪等） |
| 速報: 0B14（開催情報） | **全置換・取り消しあり**。取り逃した変更は後の RACE/YSCH 更新で追いつくことが多い | 取得のたびにスナップショット保存・差分イベント生成。長期不在は DEGRADED |
運用上の推奨: ①スリープ・休止無効化、②Windows Update のアクティブ時間設定、③UPS は任意、④ハートビート欠落をウィンドウ中に検知して Discord 通知（エージェント自身ではなくサーバ側タイマで検知）、⑤予備 PC は**別の利用キー**が必要（同一キー複数端末は不可 [二次]）。

## 7. 更新・配布
| 項目 | 設計 |
|---|---|
| 配布物 | `agent-<semver>-win-x64.zip`（Python 同梱 exe + `install.ps1`）。**秘密・利用キー・トークンを含めない** |
| 初回導入 | ユーザーが手動: JV-Link 導入 → 設定ツールで利用キー登録 → `install.ps1` → ingest 管理画面で発行した登録コードで `agent_id` とトークンを取得 |

| 自動更新 | `GET /v1/agent/update` が `{version, sha256, ed25519_sig, url}` を返す。エージェントは**署名検証 → 別ディレクトリに展開 → 切替 → 起動確認 → 失敗でロールバック**。**STOPPED/UNKNOWN 中は更新しない** |
| 署名 | Ed25519（公開鍵はエージェントに埋め込み、秘密鍵は CI のシークレット）。Windows コード署名証明書は有料のため前提にしない（SmartScreen 警告は許容、2 人利用） |

## 8. ログ・監視・障害復旧
| 項目 | 設計 |
|---|---|
| ローカルログ | `%LOCALAPPDATA%\jraagent\logs\` 日次ローテーション、30 日、レコード本文は書かない（規約・サイズ） |
| ハートビート | 60 秒ごと（NORMAL 時）: agent_version、時計ずれ、キュー深さ/最古、`acked_ts`、JV-Link 状態（直近 ret）、ディスク空き、最終エラー。サーバが `agent_heartbeat` に保存し、**開催日ウィンドウ中に 5 分欠落で警告・15 分で重大**（Discord エラー Webhook） |
| 時計ずれ | NTP と 30 秒超ずれたら警告（オッズ時系列の観測時刻が壊れるため） |
| 障害復旧 | クラッシュ→自動再起動→`outbox` から再開（PENDING/SENDING を PENDING へ戻す）。JV-Link ハング→ワーカー kill→`JVClose` 相当の再初期化→`fromtime` から再取得。ディスク満杯→取得停止+アラート |
| 診断 | `agent diagnose`: 参照元の診断スクリプト群（check_jvlink*, check_datatype_enabled 等）を 1 コマンドに集約。データ種別ごとの `JVOpen` 戻り値（-201 など）を表示 |

## 9. サーバ側（Kotlin）の取込責務と移植範囲
- **受信**: `/v1/agent/ingest`（認証、モード判定、gzip 展開、バッチ冪等）。
- **解析**: JV-Data のレコード別パーサ（RA/SE/HR/O1/O3/O5/UM/YS/WE/AV/JC/TC/CC/WH）。**ゴールデンテストの入力は実データではなく、仕様書のレイアウトから生成した合成レコード**（実データをリポジトリに置くことは複製・保管にあたり得るため禁止。DATA_SOURCE_COMPLIANCE §5）。実データでの突合は利用者のローカル環境でのみ実施する。
- **正規化**: `race_id`(12桁) を主キーに（16桁 `rt_key` は導出、D-040）。cp932→Unicode はサーバで一度だけ。
- **移植しないもの**: 診断スクリプトの試行錯誤（`test_jvopen_*` 等）— ただし得られた知見（引数の癖、戻り値）は本書 §1 と T1.17 の確認項目に転記済み。
- **統合先モジュール**: `:ingest`（新設案、D-020）+ `:domain` のパーサ。bot からは DB 経由で参照（bot と ingest は互いに依存しない）。
