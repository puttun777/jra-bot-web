## 1. 実際に必要なメモリ（この環境で実測。合成データ）

JDK 25・MySQL 8.4（Docker）。各アプリの jar を直接起動し、`/proc/<pid>` の RSS を測った。**認証が必要な API は 401 で返るため、DB を読む画面・大きな取込は測れていない**。

| プロセス | 設定 | RSS |
|---|---|---|
| MySQL 8.4 | 既定（performance_schema ON・バッファプール 128 MiB） | 約 425 MiB（空の DB） |
| MySQL 8.4 | 小さく絞る（performance_schema OFF・バッファプール 128 MiB・接続 40） | 約 135 MiB（空の DB で**実測**）。バッファプールが埋まると **約 260 MiB の見込み（未計測）** |
| dashboard | 現行（`MaxRAMPercentage=75`・上限 1 GiB 相当） | 起動後 267 → 約 3,000 リクエスト後 **275 MiB** |
| dashboard | 小さく絞る（`-Xmx160m`・SerialGC・C1 のみ） | 190 → **203 MiB** |
| ingest | 現行 | 256 → **268 MiB** |
| ingest | 小さく絞る | 189 → **200 MiB** |
| bot calendar-check | 現行 / 絞る | ピーク **197 / 164 MiB**（約 4 秒で終了） |
| bot bot-run | 現行（上限 2 GiB 相当） | 起動〜終了でピーク **228 MiB**（合成の空カレンダーで SCHEDULE_UNKNOWN 終了。**周回中のピークは未計測**） |
| ml-train | 現行の割当 4 GiB | **未計測**（データセットの大きさに比例。PC で実行する案もある） |

**結論**: 常駐は MySQL + dashboard + ingest で約 0.75 GiB、開催日は bot-run が加わり、OS・Docker を含めて**ピーク 1.3〜1.8 GiB 程度と推定**（実測の和: MySQL 260〈見込み〉+ dashboard 203〜275 + ingest 200〜268 + bot-run 228〈起動時〉+ calendar-check 等 165〜200 ≈ 1.05〜1.23 GiB。これに OS・Docker 約 0.3 GiB と bot-run の周回中の増分〈未計測〉を加えた）。現行の割当（dashboard/ingest 各 1 GiB、bot-run 2 GiB）は大きすぎ、**bot-run は 1 GiB で足りる見込み**（周回中の実測が必要: §6）。**1 GiB の e2-micro に 3 つの JVM と MySQL は載らない**（JVM を 1 つに統合する作り直しが必要）。**2 GiB の e2-small は JVM を絞りスワップを置けば載る見込み（P-1 と、5〜10 GB のデータに対するバッファプール 128 MiB の性能〈P-5〉の確認が条件）**、4 GiB の e2-medium なら余裕がある。

本人が**案 1** を選択（D-278）。IaC の既定を db-f1-micro・SSD 10 GB・予算の通知 3,000 円に変更（infra I-041。適用は本人承認後）。1a/1b は UNRESOLVED D-22。bot-run の縮小は P-1 の後。

## 8. 構成移行の前でも進める（配置先に依存しない）作業

- JVM のメモリ設定を環境変数で上書きできるようにする（`JAVA_TOOL_OPTIONS` は Cloud Run・VM・Windows で共通に使える）。

- 画面の認証を「IAP の JWT」から「署名 JWT の検証器（発行者・JWKS・aud を設定）」に一般化する設計（IAP・Cloudflare Access・自前 OIDC のどれでも使える。実装は配置先の決定後）。
